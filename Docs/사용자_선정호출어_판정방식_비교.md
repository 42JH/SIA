# 사용자 지정 호출어 — 현재 판정 방식과 B안 비교

측정일 2026-09-18. 화자 1명(본인), 호출어 3개(`춘식아`, `춘식`, `대길이`). 받아쓰기 모델은 faster-whisper small.

---

## 1. 현재 구현의 판정 방식 (A안)

"시아야"는 그 단어만 따로 학습한 전용 모델이 발음을 확인한다. 사용자가 방금 정한 단어에는 그런 모델을 만들 수
없으므로, 발음 확인을 **싸고 느슨한 1차 → 비싸고 정확한 2차** 두 단계로 나눴다.

쓰는 말
- **헤드**: 등록 녹음으로 그 자리에서 학습하는 작은 판별기(로지스틱 회귀). 입력은 공용 음성 특징(80 ms 마다
  96차원)의 최근 16프레임 = 1.28초, 1536차원이다.
- **부정 뱅크**: "호출어가 아닌 말소리"의 특징 2000개를 미리 모아 둔 파일(5.5 MB). 헤드 학습 때 오답으로 쓴다.
- **단어 확률**: 받아쓰기 모델에게 받아 적게 하지 않고, "이 소리가 이 단어일 확률"을 직접 읽은 값.
  단어를 이루는 글자 조각들의 로그확률 평균이며 0에 가까울수록 그 단어다.

등록 (호출어를 5번 부른다)
1. 부를 때마다 단어 확률 ≥ −4.5 인지, 앞 녹음과 같은 목소리인지 확인한다.
2. 5개가 모이면 녹음 하나를 속도·크기·위치를 바꿔 30개로 늘려 정답 150개를 만든다.
3. 정답 150개와 부정 뱅크 2000개로 헤드를 학습한다.
4. 헤드와 목소리 정보를 등록 파일 하나(`wake.npz`, 약 25 KB)에 담아 PC 와 서버에 저장한다.

실행 (부를 때마다)
1. **1차-상시 — 헤드 ≥ 0.1.** 말하는 도중에 마이크 소리를 계속 채점해, 넘지 못한 소리는 뒤 단계로 넘기지 않는다.
2. **1차-발화 — 헤드 ≥ 0.5.** 말이 끝나면 그 발화를 통째로 다시 채점한다. 느슨해서 다른 말도 꽤 통과시킨다.
3. **목소리 확인 — 유사도 ≥ 0.35.** 등록 때 목소리와 닮았는지 본다. "시아야"와 같은 단계다.
4. **2차 — 단어 확률 ≥ −4.0.** 여기까지 온 소리에만 받아쓰기 모델을 돌린다.
5. 모두 통과하면 세션을 연다.

1차의 기준이 두 개인 이유는 4절에 적었다 — 같은 호출이라도 말하는 도중에 매긴 점수와 말이 끝난 뒤 매긴
점수가 크게 다르다.

### 1차 헤드가 내는 점수

헤드는 최근 1.28초의 소리(숫자 1536개)를 받아 "호출어일 확률" 0~1 하나를 낸다. 학습 때 정답 150개와 오답
2000개를 가르는 경계선 하나를 찾아 두고, 실행 때는 새 소리가 그 선의 어느 쪽에 얼마나 멀리 있는지를 확률로
바꾼다. 계산은 곱셈 한 번이라 80 ms 마다 돌려도 부담이 없다. 오답이 "낭독과 영상 소리"뿐이라 경계가 느슨하고,
그래서 기준을 낮게 두고 2차에 맡긴다.

**같은 헤드를 두 자리에서 쓰는데 점수 분포가 달라 기준도 둘이다.** 말하는 도중에는 방금 들어온 1.28초만
채점하므로 호출어가 창 안에 반쯤 걸쳐 점수가 낮게 나온다. 말이 끝난 뒤에는 앞뒤에 무음을 1초씩 붙이고 창을
80 ms 씩 밀어 가며 가장 높은 점수를 고르므로 같은 호출도 훨씬 높게 나온다.

| 채점하는 자리 | 본인 호출 | 사람 말이 없는 배경 | 기준 |
|---|---|---|---|
| 말하는 도중 (상시) | 0.114 ~ 0.933 (13건, 중앙 0.219) | 1.5분에서 최고 0.155, 0.1 을 넘은 것 1번 (0.3 이상은 없다) | 0.1 |
| 말이 끝난 뒤 (발화 통째) | 0.860 ~ 1.000 (14건) | — (뒤 단계에서 거절된 발화 14건 중 14건이 0.1 을, 8건이 0.5 를 넘었다) | 0.5 |

말하는 도중의 점수는 본인 호출(최저 0.114)과 배경(최고 0.155)이 겹쳐서, 기준을 올리면 오탐이 아니라
진짜 호출이 먼저 사라진다. 그래서 이 자리는 0.1 로 두고, 말이 끝난 뒤의 채점만 0.5 로 올렸다 — 본인 호출
14건이 모두 통과하면서 뒤 단계(목소리 확인·받아쓰기)를 부르는 횟수를 줄인다.

**사람이 말을 하고 있으면 헤드는 기준과 무관하게 터진다.** 다른 호출어(`시아야`)로 부른 본인 발화 8분을
`철수야` 헤드로 흘리자 최고점이 1.000 이었고, 0.1 에서 분당 5.6회, 0.7 로 올려도 분당 2.6회 넘었다.
거절된 발화 14건 중 6건이 발화 통째 채점에서 0.9 를 넘은 것도 같은 이야기다 — 비슷한 말을 가르는 일은
헤드의 몫이 아니라 2차의 몫이다.

측정은 2026-09-18, 호출어 `철수야`, 조용한 방에서 본인 호출 14회다. 배경과 다른 호출어 발화는 이전에
녹음해 둔 9.5분(유튜브를 틀어 둔 방에서 `시아야`로 부른 발화 8분, 사람 말이 없는 배경 1.5분)을 다시 흘려 쟀다.

### 2차 단어 확률의 원리

**받아쓰기 모델은 원래 객관식으로 글자를 고른다.** 소리를 듣고 글자 조각을 하나씩 써 내려가는데, 조각을 쓸
때마다 수만 개 후보 전부에 확률을 매긴 뒤 1등만 남긴다.

```
소리: 짧게 부른 "춘식아"                (아래 숫자는 설명용 예시)

첫 조각 후보    확률
  "순"         40 %   ← 1등. 받아쓰기는 이것을 고른다
  "춘"         35 %   ← 2등. 받아쓰기에서는 버려진다
  "탐"         10 %
  ...
```

1등이 "순"이면 다음 조각은 "순" 뒤에 올 법한 글자가 되고, 결과는 `순식`이 된다. 모델은 이 소리가 `춘식아`일
가능성을 35 % 로 높게 봤지만, 1등만 남기는 규칙 때문에 그 정보가 사라진다. B안의 2차가 호출을 놓치는 이유다.

**A안은 답을 정해 주고 점수만 받는다.** 받아 적게 하지 않고 이렇게 묻는다.

```
질문: "이 소리가 '춘' → '식' → '아' 순서였다고 치면, 각 조각의 확률이 얼마였나?"
답:    춘 35 %,  식 60 %,  아 70 %
```

세 값을 하나로 합친 것이 단어 확률이다. 각 확률에 자연로그를 취해 평균을 낸다.

```
단어 확률 = ( ln 0.35 + ln 0.60 + ln 0.70 ) ÷ 3 = ( −1.05 − 0.51 − 0.36 ) ÷ 3 = −0.64
```

- 값은 항상 0 이하다. 0 에 가까울수록 그 단어이고, −5 나 −6 이면 전혀 아니라는 뜻이다.
- 로그를 쓰는 이유: 조각 하나라도 확률이 0.1 % 처럼 바닥이면(ln 0.001 = −6.9) 평균이 크게 깎인다. 앞 두 글자만
  비슷하고 끝이 다른 말을 걸러 내려는 것이다. 그냥 평균을 내면 한 조각의 낙제가 묻힌다.
- 평균을 내는 이유: 호출어 글자 수가 달라도 같은 기준(−4.0)을 쓰기 위해서다.
- 모델이 한 글자를 여러 조각으로 쪼개는 경우가 있어, 단어 앞에 공백을 붙인 쪼개기와 안 붙인 쪼개기 두 가지로
  계산해 높은 쪽을 쓴다.

**실제로 어떻게 갈리는가.** 이전 측정(호출어 `철수야`, 본인 녹음)의 단어 확률 중앙값이다.

| 들려준 소리 | 단어 확률 | 기준 −4.0 |
|---|---|---|
| 실제 호출 | −2.2 | 통과 |
| 한 글자 다른 단어 (찰수야 등) | −3.8 | 절반쯤 통과 — 알려진 약점 |
| 다른 호출어 ("시아야") | −4.9 | 탈락 |
| 무관한 말 | −5.7 | 탈락 |

이번 측정의 호출어는 `춘식아` 중앙값 −1.21, `춘식` −2.06 이었다. 2글자는 기준까지의 여유가 0.85 줄어든다.

**왜 빠른가.** 받아쓰기는 글자를 하나 만들고 그 결과로 다음 글자를 만드는 일을 반복한다. 단어 확률은 소리를
한 번 읽은 뒤 정해진 조각들의 확률만 꺼내면 끝난다. 같은 모델인데 GPU 에서 0.109초 대 0.049초다 (4절).

**새 모델이나 학습이 필요 없다.** 받아쓰기 모델이 단어별 시각을 계산할 때 쓰는 기능을 그대로 쓴다. 호출어가
바뀌면 물어볼 글자만 바꾸면 된다.

## 2. 비교 대상 (B안)

| | A안 (현재) | B안 |
|---|---|---|
| 1차 | 헤드 ≥ 0.1 (말하는 도중) · ≥ 0.5 (말이 끝난 뒤) | 등록 녹음 5개의 특징과 코사인 유사도 ≥ 0.45 |
| 2차 | 단어 확률 ≥ −4.0 | 받아쓰기 결과에 호출어 글자가 들어 있는가 |
| 등록 때 학습 | 있음 | 없음 |

1차 입력 특징, 받아쓰기 모델, 등록 녹음 5개는 두 방식이 같다. 목소리 확인도 같아서 비교에서 뺐다.

## 3. 정확도

괄호 없이 통과 수 / 전체. 받아쓰기 모델은 GPU.

### 부른 것을 잡는가

| 호출어 | 조용한 곳 A안 | 조용한 곳 B안 | 유튜브 틀고 A안 | 유튜브 틀고 B안 |
|---|---|---|---|---|
| 춘식아 | **20 / 20** | 18 / 20 | **7 / 8** | 3 / 8 |
| 춘식 | **19 / 20** | 13 / 20 | **4 / 8** | 0 / 8 |
| 대길이 | **20 / 20** | 19 / 20 | 8 / 8 | 8 / 8 |

### 부르지 않은 소리를 받아들이는가 (호출어 3개 공통)

| 세트 | 개수 | A안 | B안 |
|---|---|---|---|
| 본인이 "시아야"라고 부른 녹음 | 50 | 0 | 0 |
| 본인의 다른 말 | 140 | 0 | 0 |
| 여러 사람의 잡담 | 120 | 0 | 0 |
| 다른 호출어 (대길이 ↔ 춘식) | 20 | 0 | 0 |

### 등록이 되는가 (등록 녹음 5개가 2차 검사를 통과하는 수)

| 호출어 | A안 (단어 확률 ≥ −4.5) | B안 (받아쓰기에 호출어 포함) |
|---|---|---|
| 춘식아 | 5 / 5 | 4 / 5 |
| 춘식 | 5 / 5 | **2 / 5** |
| 대길이 | 5 / 5 | 5 / 5 |

A안은 15개 중 가장 낮은 값이 −4.03 이었다. B안은 `춘식`이 `순식`, `탐색`으로 적혀, 또박또박 불러도 등록이
끝나지 않는다.

## 4. 시간

호출어 `춘식아`, 조용한 호출 20개의 발화당 중앙값.

| 단계 | GPU | CPU |
|---|---|---|
| A안 1차 (헤드 채점) | 0.033 s | 0.032 s |
| A안 2차 (단어 확률) | **0.049 s** | **1.396 s** |
| **A안 합계** | **0.082 s** | **1.428 s** |
| B안 1차 (유사도 채점) | 0.017 s | 0.018 s |
| B안 2차 (받아쓰기) | 0.109 s | 1.615 s |
| **B안 합계** | **0.126 s** | **1.633 s** |

- 1차는 두 방식 모두 onnxruntime 이라 GPU 가 있어도 CPU 에서 돈다. 장치 차이는 2차에서만 난다.
- 2차는 A안이 GPU 에서 2.2배, CPU 에서 1.16배 빠르다. 글자를 하나씩 만들어 내는 단계가 없어서다.
- CPU 로 바꿔도 정확도는 같았다. A안 2차는 GPU·CPU 모두 20 / 20, B안 2차는 18 / 20 → 17 / 20.
- 2차는 1차가 통과시킨 소리에만 돈다. 매 발화마다 도는 것은 1차뿐이다.

한 번만 드는 시간 (A안만 해당)

| 항목 | 시간 | 언제 |
|---|---|---|
| 헤드 학습 (특징 추출 150회 포함) | CPU 약 3 s | 등록 5번째 녹음 직후 1회 |
| 상시 1차 채점 | 30 ms 블록당 약 1 ms (CPU) | 실행 중 계속 |

B안은 등록 때 학습이 없다. 상시 채점 비용은 두 방식이 같은 급이다.

## 5. 결론

정확도, 시간, 등록 가능 여부 모두 A안이 낫다. 부르지 않은 소리는 두 방식 모두 310개 중 0건으로 같고, 차이는
"부른 것을 놓치는가"에서 난다. B안은 짧은 호출어를 등록조차 못 하므로 대안이 되지 못한다. **A안을 유지한다.**

GPU 가 없는 PC 에서는 어느 방식이든 호출 한 번에 1.4~1.6초가 더 걸린다.

표본: 조용한 호출 20개, 유튜브 8개, 부정 310개, 화자 1명. 유튜브 칸은 1건이 12.5 %p 다.
